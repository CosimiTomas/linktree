Introducción

3.1 Propósito

El presente proyecto tiene como objetivo el desarrollo del Sistema de Gestión de Vacunas (SGV), una aplicación web destinada al vacunatorio del CAPS San José Obrero de Hurlingham, Buenos Aires.

En la actualidad, el vacunatorio no cuenta con ningún sistema de control interno de stock de vacunas. El registro de cada dosis aplicada se realiza de forma manual y por triplicado,en la planilla física (hoja 10), en la historia clínica del paciente y en la Intranet provincial, mientras que el control de existencias y de vencimientos se lleva de manera visual y sin respaldo digital. Esta ausencia de un registro interno unificado genera dificultades para conocer el stock real disponible, anticipar los vencimientos y detectar faltantes a tiempo.

El SGV busca cubrir ese vacío operativo, brindando una herramienta que permita registrar los movimientos de vacunas (ingreso de lotes, aplicaciones y descartes), consultar el stock actualizado en dosis, y recibir alertas automáticas ante niveles bajos de existencias y próximos vencimientos. De este modo, el sistema apunta a reducir los errores de control, evitar la pérdida de dosis por vencimiento y ordenar la gestión interna del vacunatorio, sin reemplazar los registros oficiales externos que el personal de enfermería ya está obligado a completar.

3.2 Alcance

El Sistema de Gestión de Vacunas comprende la gestión interna del stock de vacunas del vacunatorio del CAPS San José Obrero. El desarrollo actual abarca las siguientes funcionalidades:

El desarrollo actual abarca:

  • Gestión del catálogo de vacunas: alta y baja de los tipos de vacunas disponibles en el sistema, a cargo exclusivo del rol de coordinadora.
  • Registro de movimientos de stock: ingreso de lotes (con número de lote, fecha de vencimiento y cantidad de dosis), registro de aplicaciones y registro de descartes de dosis o frascos con motivo obligatorio (vencimiento, corte de cadena de frío o rotura). Estas operaciones corresponden al rol de enfermería.
  • Control de existencias en dosis: el sistema almacena y calcula el stock disponible en dosis, mostrando de forma derivada la cantidad de frascos en el caso de las vacunas multidosis.
  • Sistema de alertas automáticas: el sistema genera tres tipos de alertas jerarquizadas por gravedad: stock bajo, lotes próximos a vencer y lotes vencidos, permitiendo anticipar faltantes y evitar la aplicación o la conservación de dosis vencidas.
  • Gestión de usuarios y roles: administración de las cuentas del personal (alta, baja, modificación y cambio de contraseñas), a cargo del rol de coordinadora, con autenticación segura.
  • Panel de control (dashboard): visualización centralizada de las alertas y de los indicadores principales del vacunatorio al iniciar sesión, con las pestañas habilitadas según el rol del usuario.
  • Exportación de datos a formato Excel: el sistema permite descargar cuatro tipos de reportes en formato .xlsx: stock general del vacunatorio, stock detallado por vacuna específica, historial de movimientos filtrado por fecha, y reporte de reposición (este último disponible exclusivamente para el perfil Proveedora). Estos reportes facilitan el envío de información a la Región Sanitaria y el uso administrativo.
  • El sistema contempla cuatro roles con permisos diferenciados: enfermería (operación completa del stock y del registro de movimientos), coordinadora (gestión de usuarios y del catálogo de vacunas), y proveedora y jefatura de enfermería (acceso de solo lectura, orientado a la consulta de stock y a la elaboración de reportes).

Quedan fuera del alcance del desarrollo actual:

  • El descuento automático de stock a partir de la aplicación registrada en los sistemas oficiales. Esto requeriría acceso al sistema municipal de Historia Clínica, de carácter privado e inaccesible para el equipo. Por lo tanto, la baja de dosis en el SGV se realiza mediante el registro manual de aplicaciones y descartes.
  • La integración con los sistemas oficiales externos (planilla hoja 10, historia clínica e Intranet provincial), que son sistemas nacionales y provinciales privativos. El personal de enfermería continúa completando esos registros por obligación normativa; el SGV cubre el control interno que hoy no existe, sin reemplazarlos.
  • La identificación del responsable de cada movimiento, dado que el personal ya identifica cada aplicación con su sello personal en la historia clínica oficial.
  • La gestión de datos de pacientes, historias clínicas, asignación de turnos o identificación por DNI, que exceden el objetivo del sistema.

3.6 Resumen Ejecutivo

El Sistema de Gestión de Vacunas (SGV) es una aplicación web desarrollada para el vacunatorio del CAPS San José Obrero de Hurlingham, Buenos Aires, con el objetivo de resolver una necesidad concreta: en la actualidad, el vacunatorio no cuenta con ningún sistema interno de control de stock, y la gestión de existencias, vencimientos y descartes se realiza de forma visual y manual, lo que genera errores frecuentes, pérdida de dosis y una alta carga de trabajo para el personal.

El sistema permite registrar los movimientos de vacunas (ingreso de lotes, aplicaciones y descartes), consultar el stock actualizado en dosis, y recibir alertas automáticas ante niveles bajos de existencias, lotes próximos a vencer y lotes vencidos. Además, ofrece un panel de control centralizado, la gestión del catálogo de vacunas y la administración de usuarios con permisos diferenciados por rol.

El público objetivo está compuesto por cuatro roles del vacunatorio: enfermería (operación diaria del stock), coordinadora de enfermería (gestión de usuarios y del catálogo de vacunas), y proveedora y jefatura de enfermería (consulta y elaboración de reportes). El sistema fue diseñado para uso en computadora, en base a las condiciones reales de trabajo relevadas en el CAPS.

Como principales resultados esperados, el SGV apunta a: reducir la pérdida de dosis por vencimiento gracias al sistema de alertas anticipadas; ofrecer por primera vez un registro interno unificado y confiable del stock disponible; disminuir el tiempo dedicado al control manual; y aportar información ordenada que facilite la elaboración de los reportes que el vacunatorio envía a la Región Sanitaria. Todo ello, sin reemplazar los registros oficiales externos (planilla hoja 10, historia clínica e Intranet provincial) que el personal debe seguir completando por obligación normativa.

El proyecto fue desarrollado por el Equipo N.° 01 de 7.° Informática del Instituto Leonardo Murialdo durante el ciclo lectivo 2026, con la participación del equipo de enfermería del vacunatorio del CAPS San José Obrero en las instancias de relevamiento y validación, y con la Lic. Mariana Touzon como interlocutora principal y clienta del proyecto.

Descripción General

4.1 Perspectiva del producto

El Sistema de Gestión de Vacunas es un sistema nuevo, desarrollado desde cero para cubrir un vacío operativo del vacunatorio del CAPS San José Obrero. En la actualidad, el vacunatorio no cuenta con ninguna herramienta interna de control de stock; el SGV no reemplaza ni mejora un sistema preexistente, sino que introduce una funcionalidad que hoy no existe en el ámbito de trabajo del personal de enfermería.

Si bien es técnicamente autónomo, el sistema no opera de manera aislada: se integra al flujo de trabajo diario del vacunatorio, comparte el mismo dominio de información (vacunas, lotes, aplicaciones) que los registros oficiales, y está pensado para ser utilizado desde la misma computadora del sector, en el mismo espacio físico donde se conservan las vacunas.

El sistema convive con los registros oficiales externos que el personal ya utiliza,la planilla física (hoja 10), la historia clínica del paciente y la Intranet provincial, pero no se integra con ellos. Esta decisión responde a que dichos sistemas son nacionales y provinciales de carácter privativo, sin interfaces públicas disponibles para el equipo desarrollador. En consecuencia, el SGV opera como una capa de control interno paralela y complementaria, orientada exclusivamente a la gestión del stock del vacunatorio.

Desde el punto de vista arquitectónico, el SGV es una aplicación web full-stack compuesta por un frontend accesible desde el navegador, un backend que expone una API REST y una base de datos relacional que almacena la información del sistema. Está pensado para ser accedido desde la computadora del vacunatorio, en el mismo espacio físico donde se conservan las vacunas.

Aunque el desarrollo inicial se realizó específicamente para el CAPS San José Obrero, el sistema fue diseñado como un producto escalable y adaptable, susceptible de ser implementado en otros vacunatorios y centros de salud municipales con necesidades similares, mediante ajustes mínimos de configuración.

4.2 Funcionalidad del producto

El Sistema de Gestión de Vacunas ofrece al vacunatorio del CAPS San José Obrero un conjunto de funcionalidades organizadas en cinco bloques principales, orientados a cubrir el ciclo completo de gestión interna del stock de vacunas.

  • Autenticación y control de acceso. El sistema requiere el inicio de sesión de cada usuario mediante credenciales personales, y a partir de la validación de su identidad y su rol, habilita únicamente las pestañas y las acciones que le corresponden. De este modo, cada perfil accede a una vista diferenciada del sistema, adaptada a sus responsabilidades dentro del vacunatorio.
  • Gestión del catálogo de vacunas. El sistema permite mantener actualizado el listado de tipos de vacunas disponibles en el vacunatorio, incluyendo información como el nombre, la cantidad de dosis por frasco y el umbral de stock bajo. Esta funcionalidad permite dar de alta nuevas vacunas cuando ingresan al catálogo del CAPS y dar de baja las que dejan de utilizarse.
  • Gestión operativa del stock. El sistema permite registrar los tres movimientos que modifican el stock de vacunas: el ingreso de nuevos lotes (con su número de lote, fecha de vencimiento y cantidad de dosis), el registro de aplicaciones sobre lotes existentes, y el registro de descartes con motivo obligatorio (vencimiento, corte de cadena de frío o rotura). En todos los casos, el sistema recalcula automáticamente el stock disponible y actualiza las alertas correspondientes. Además, el sistema incluye un módulo de gestión de frascos multidosis: al registrar la apertura de un frasco de una vacuna multidosis (Hepatitis B, Doble bacteriana dT, dTpa y Salk), el sistema registra la fecha de apertura y calcula automáticamente su fecha de vencimiento como el menor valor entre los 30 días posteriores a la apertura y la fecha de vencimiento del lote, garantizando el control de la vida útil del frasco abierto.
  • Visualización de información y sistema de alertas. El sistema ofrece un panel de control (dashboard) que se muestra al iniciar sesión, con las alertas activas y los indicadores principales del vacunatorio. Las alertas se organizan en tres niveles según su gravedad: stock bajo, lotes próximos a vencer y lotes vencidos, permitiendo al personal anticipar faltantes, priorizar el uso de los lotes con vencimiento más cercano y evitar la aplicación o conservación de dosis vencidas. Además, el sistema ofrece vistas detalladas del stock por vacuna, por lote y por movimiento histórico.
  • Gestión de usuarios. El sistema permite administrar las cuentas del personal habilitado para operar la aplicación, incluyendo el alta, la baja y la modificación de usuarios, así como el cambio de contraseñas. Esta funcionalidad se encuentra restringida a un rol específico, encargado de mantener actualizado el padrón de usuarios del sistema.
  • Exportación de datos a formato Excel. El sistema permite exportar cuatro tipos de reportes en formato .xlsx: stock general del vacunatorio, stock detallado por vacuna específica, historial de movimientos filtrado por rango de fechas, y reporte de reposición (exclusivo del perfil Proveedora). Estos reportes se descargan automáticamente al hacer clic en el botón de exportación desde la sección correspondiente, listos para abrir con Microsoft Excel o Google Sheets.

4.4.2 Limitaciones de hardware

El Sistema de Gestión de Vacunas es una aplicación web que se ejecuta íntegramente en el navegador, sin requerir instalación local ni componentes de hardware específicos. El sistema es accesible tanto desde una computadora como desde un celular con navegador web y conexión a Internet, y su interfaz es responsive (se adapta visualmente al tamaño de la pantalla del dispositivo).

El vacunatorio del CAPS San José Obrero cuenta con una única computadora, una EXO AIO Style H7B-T5488 (All-in-One, industria argentina), equipada con procesador Intel Core i5-7400, 8 GB de memoria RAM DDR4 y disco rígido de 500 GB, con sistema operativo Windows 10 Pro y navegador Google Chrome. Estas especificaciones superan holgadamente los requisitos mínimos del sistema, que se limitan a un navegador compatible con JavaScript moderno (ES6+) y una conexión a Internet. Además, el personal puede acceder al sistema desde su celular personal a través del navegador, lo que permite consultar el stock y las alertas sin depender de la disponibilidad de la computadora del vacunatorio.

La conexión a Internet del CAPS es provista por WiFi institucional. Según lo relevado en la entrevista con el equipo de enfermería, la conexión no siempre es estable, lo que constituye la principal limitación de hardware del entorno: si el CAPS pierde conectividad, el sistema queda inaccesible desde la computadora del vacunatorio hasta que se restablezca el servicio. Desde un celular con datos móviles, el sistema seguiría siendo accesible con independencia del WiFi del CAPS.

Del lado del servidor, el SGV se aloja en Railway, una plataforma de hosting en la nube que provee el entorno de ejecución (Node.js) y la base de datos (MySQL) como servicios gestionados. El equipo no administra servidores físicos propios. Railway ofrece disponibilidad continua con HTTPS, aunque el plan gratuito tiene limitaciones de recursos (horas de cómputo mensuales y almacenamiento) que requieren la migración a un plan pago para garantizar el funcionamiento continuo del sistema en producción. En caso de que el CAPS adopte el sistema de forma permanente, deberá asumir el costo del hosting (estimado en USD 60 anuales según los valores de referencia de la sección 7.2).

4.4.3 Interfaces con otras aplicaciones

El Sistema de Gestión de Vacunas no se integra con ninguna aplicación externa. Opera como un sistema autónomo de control interno del stock del vacunatorio.

En el entorno del CAPS, el personal utiliza dos sistemas oficiales para el registro de las vacunas aplicadas: la historia clínica digital del municipio de Hurlingham y la Intranet provincial de registro de vacunación. Ambos son sistemas de acceso restringido, sin interfaces públicas (APIs) disponibles para terceros, por lo que la integración técnica no es viable para el equipo desarrollador. El SGV convive con estos sistemas como una capa complementaria, sin intercambiar datos con ellos.

No se prevén integraciones futuras con estos sistemas en el alcance actual del proyecto.

4.4.4 Función de control

El sistema implementa los siguientes mecanismos de control de acceso:

Autenticación. Cada usuario accede al sistema mediante credenciales personales (correo electrónico y contraseña). Las contraseñas se almacenan cifradas con el algoritmo bcrypt (hash con sal), de modo que no quedan guardadas como texto plano en la base de datos. La sesión del usuario se gestiona mediante JSON Web Token (JWT), que firma la identidad y el rol del usuario y se valida en el servidor en cada petición.

Autorización granular por roles. El sistema define cuatro roles con un modelo de permisos granular basado en cinco flags que se combinan según el rol: escritura (permite crear lotes, aplicar dosis y registrar descartes), gestión de usuarios (permite administrar cuentas y el catálogo de vacunas), acceso a movimientos (habilita la pestaña de historial y sus reportes), acceso al resumen de actividad (activa el panel de indicadores de gestión) y perfil de proveedora (activa la vista simplificada de reposición). Las restricciones se aplican tanto en la interfaz como en el servidor, impidiendo que un usuario acceda a funcionalidades restringidas aunque manipule la petición manualmente.

Gestión de credenciales. Los usuarios son creados y administrados exclusivamente por el rol de coordinadora. No existe un registro público ni una recuperación de contraseña autónoma: si un usuario necesita un cambio de contraseña, la coordinadora lo realiza desde su panel de gestión.

4.4.5 Requisitos del lenguaje

Toda la interfaz del sistema está desarrollada en español rioplatense, incluyendo los menús, los botones, los formularios, las tablas, los mensajes de error y las alertas. Se utiliza terminología familiar al ámbito sanitario y al vocabulario cotidiano del personal de enfermería (por ejemplo, "lote", "dosis", "frasco", "descarte por rotura"), evitando jerga técnica de desarrollo de software.

El manual de uso del sistema seguirá el mismo criterio de lenguaje: redacción clara, en español y orientada al usuario final, sin suponer conocimientos de informática por parte del lector. (Apartado a completar una vez finalizado el manual de uso.)

4.4.6 Protocolos señalados

El sistema utiliza los siguientes protocolos y estándares de comunicación:

HTTP/HTTPS. Toda la comunicación entre el navegador del usuario y el servidor se realiza mediante el protocolo HTTP sobre TLS (HTTPS), garantizando que los datos viajan cifrados entre el cliente y el servidor. El certificado HTTPS es provisto automáticamente por la plataforma de hosting Railway.

REST (Representational State Transfer). La comunicación entre el frontend y el backend del sistema se estructura como una API REST: el cliente envía peticiones HTTP (GET, POST, PUT, DELETE) a endpoints específicos del servidor, que responde en formato JSON. Cada petición incluye el token JWT del usuario para su autenticación.

TCP/SQL. La comunicación entre el backend y la base de datos MySQL se realiza por conexión TCP directa, mediante consultas SQL parametrizadas que previenen inyecciones de código.

Integración GitHub → Railway (CI/CD). El código fuente del sistema se aloja en un repositorio de GitHub. Railway está vinculado a dicho repositorio y, ante cada actualización (push) en la rama principal, despliega automáticamente la nueva versión del sistema en producción. Esta integración continua permite que los cambios en el código se reflejen en el sistema en funcionamiento sin intervención manual.

4.4.7 Requisitos de fiabilidad

El SGV es una herramienta de control interno complementaria a los registros oficiales del vacunatorio. Una interrupción temporal del servicio no compromete la operación del CAPS ni la atención al paciente, dado que el personal continúa registrando las aplicaciones en la historia clínica e Intranet provincial con independencia del sistema. No obstante, se establecen los siguientes requisitos de fiabilidad para garantizar la utilidad operativa del sistema:

Disponibilidad. El sistema debe estar accesible las 24 horas del día, los 7 días de la semana. Si bien el vacunatorio opera de lunes a viernes de 8:00 a 17:00, el equipo de enfermería confirmó la necesidad de poder acceder al sistema fuera del horario laboral para corroborar información ante eventuales inconvenientes. La plataforma Railway provee disponibilidad continua con HTTPS, aunque el plan gratuito tiene limitaciones de recursos que podrían requerir migración a un plan pago para garantizar este nivel de servicio de forma sostenida.

Persistencia de datos. Toda la información registrada en el sistema (lotes, aplicaciones, descartes, frascos abiertos, alertas) se almacena en la base de datos MySQL gestionada por Railway. Los datos persisten aunque el servidor se reinicie. La pérdida de datos por falla de la plataforma es un riesgo residual inherente al uso de un servicio cloud gratuito.

Tolerancia a la desconexión. Si la conexión a Internet del CAPS se interrumpe, el sistema queda inaccesible desde la computadora del vacunatorio. Sin embargo, sigue siendo accesible desde un celular con datos móviles. Una vez restablecida la conexión, el sistema retoma su funcionamiento normal sin pérdida de datos ni necesidad de intervención manual.

Consistencia de las operaciones. Las operaciones que modifican el stock (aplicaciones y descartes) se ejecutan dentro de transacciones con bloqueo de fila en la base de datos, lo que garantiza que dos operaciones simultáneas no dejen el stock en un estado inconsistente.

4.4.8 Credibilidad de la aplicación

La confianza del personal del vacunatorio en el sistema se sustenta en los siguientes factores:

Datos reales del CAPS. El catálogo de vacunas del sistema fue precargado con las 18 vacunas reales del vacunatorio, con sus nombres oficiales, la cantidad de dosis por frasco y la identificación de las cuatro vacunas multidosis (Hepatitis B, Doble bacteriana dT, dTpa y Salk). El personal reconoce inmediatamente las vacunas con las que trabaja a diario.

Coherencia con la operación real. El flujo de trabajo del sistema (ingresar lote → aplicar → descartar) replica el flujo real del vacunatorio, y la terminología utilizada es la misma que el personal maneja cotidianamente. El sistema no introduce conceptos ajenos a su rutina.

Validación con el equipo de enfermería. El diseño del sistema fue validado en dos instancias formales con el equipo de enfermería del vacunatorio, a través de la Lic. Mariana Touzon como interlocutora principal (entrevista de relevamiento y entrevista de validación del mockup), y mediante un formulario de relevamiento respondido por el personal de enfermería. Las funcionalidades y la interfaz responden a lo que el equipo solicitó y validó, no a decisiones unilaterales del equipo desarrollador.

Alertas verificables. Las alertas del sistema (stock bajo, próximo a vencer y vencido) se basan en datos objetivos (cantidades de dosis y fechas de vencimiento registradas), no en estimaciones. El personal puede contrastar lo que muestra el sistema con lo que observa físicamente en la heladera.

4.4.9 Consideraciones de seguridad

El sistema implementa las siguientes medidas de seguridad para proteger la información del vacunatorio y garantizar que cada usuario acceda únicamente a las funciones que le corresponden:

Cifrado de contraseñas. Las contraseñas de los usuarios se almacenan en la base de datos como hash generado con el algoritmo bcrypt (hash con sal). En ningún momento se guardan ni se transmiten como texto plano. Esto asegura que, incluso ante un acceso no autorizado a la base de datos, las contraseñas no puedan ser leídas ni reutilizadas.

Comunicación cifrada. Toda la comunicación entre el navegador del usuario y el servidor se realiza sobre HTTPS (TLS), lo que impide la interceptación de datos en tránsito. El certificado es provisto y renovado automáticamente por Railway.

Control de acceso granular por roles. Cada usuario tiene asignado un rol (enfermería, coordinadora, jefa de enfermería o proveedora) que determina a qué funcionalidades puede acceder, mediante un modelo de permisos basado en cinco flags combinados. Las restricciones se aplican en dos niveles: en la interfaz (ocultando las pestañas, botones y paneles que no corresponden al rol) y en el servidor (cada endpoint de la API valida el rol del token JWT antes de ejecutar la operación). Este doble control impide que un usuario acceda a funcionalidades restringidas aunque manipule la petición manualmente.

Sesiones con expiración. El token JWT que firma la sesión del usuario tiene una duración limitada. Una vez expirado, el usuario debe volver a iniciar sesión. Esto reduce el riesgo de que una sesión olvidada o un dispositivo desatendido permita el acceso no autorizado al sistema.

Prevención de inyección SQL. Las consultas a la base de datos se realizan mediante consultas parametrizadas, lo que previene ataques de inyección de código SQL a través de los formularios del sistema.

Ausencia de datos sensibles de pacientes. El sistema no almacena datos personales de pacientes (nombre, DNI, historia clínica, diagnóstico ni ningún dato identificatorio). La información que gestiona es exclusivamente operativa del vacunatorio: tipos de vacunas, lotes, cantidades de dosis y movimientos de stock. Esta decisión de diseño reduce significativamente el riesgo en materia de protección de datos personales.

4.5 Suposiciones y dependencias

El desarrollo y la implementación del Sistema de Gestión de Vacunas se basan en las siguientes suposiciones y dependen de los siguientes factores externos, que están fuera del control directo del equipo desarrollador:

  • Conectividad a Internet en el CAPS. Se asume que el vacunatorio mantiene una conexión a Internet funcional durante el horario de trabajo. Si bien la conexión WiFi del CAPS no es siempre estable (según lo relevado con el equipo de enfermería), el sistema requiere conectividad para operar. En caso de corte, el personal puede acceder desde su celular con datos móviles como alternativa.
  • Disponibilidad de la plataforma Railway. El sistema depende de la infraestructura de Railway para su ejecución y para el alojamiento de la base de datos. Una interrupción del servicio de Railway dejaría al sistema inaccesible hasta su restablecimiento. Esta dependencia es inherente al modelo de hosting cloud utilizado.
  • Continuidad del navegador y del sistema operativo. Se asume que la computadora del vacunatorio mantiene un navegador actualizado compatible con JavaScript moderno (ES6+). Actualmente opera con Google Chrome sobre Windows 10 Pro, ambos con soporte vigente.
  • Compromiso del personal con el uso del sistema. El éxito operativo del SGV depende de que el personal de enfermería incorpore el registro de movimientos en el sistema como parte de su rutina de trabajo. El sistema no reemplaza los registros oficiales, por lo que su uso representa una tarea adicional para el personal. La adopción efectiva depende de que el equipo perciba el beneficio del control de stock como superior al esfuerzo de la carga.
  • Estabilidad del catálogo de vacunas. Se asume que el catálogo de vacunas del vacunatorio no sufre cambios frecuentes. El sistema permite agregar y dar de baja vacunas, pero modificaciones masivas en el catálogo (por ejemplo, un cambio en el calendario nacional de vacunación) podrían requerir una intervención de la coordinadora para actualizar el sistema.
  • Marco institucional del proyecto. El desarrollo se enmarca dentro del trabajo integrador de 7.° Informática del Instituto Leonardo Murialdo. La continuidad del proyecto más allá del ciclo lectivo 2026 (mantenimiento, actualizaciones, soporte técnico) no está garantizada y dependerá de acuerdos futuros entre el equipo, la institución y el CAPS.

4.6 Evolución previsible del sistema

En su versión actual, el SGV es una herramienta de uso interno destinada exclusivamente al personal del vacunatorio del CAPS San José Obrero: permite registrar movimientos de stock, consultar existencias y recibir alertas, en el marco de la operación diaria del equipo de enfermería. No obstante, el sistema fue diseñado con una arquitectura que permite su crecimiento y adaptación a nuevos contextos de uso. En caso de que el SGV se implemente a nivel municipal, abarcando la red de CAPS del partido de Hurlingham u otros municipios, se abriría la posibilidad de incorporar funcionalidades que hoy exceden el alcance del proyecto, como la consolidación del stock de todos los vacunatorios en un único panel, la distribución automatizada de vacunas desde el depósito central del Hospital Municipal, o la generación de reportes comparativos entre centros de salud. A continuación se describen las líneas de evolución previstas:

  • Adaptación a otros vacunatorios y municipios. El SGV fue desarrollado para el CAPS San José Obrero de Hurlingham, pero su diseño es lo suficientemente genérico como para ser implementado en otros vacunatorios de la red municipal o de otros municipios con necesidades similares. La adaptación requiere ajustes mínimos de configuración: el catálogo de vacunas se gestiona desde el propio sistema (alta y baja por la coordinadora), y la identidad visual (paleta de colores, logo institucional y nombre del centro de salud) es configurable sin necesidad de modificar el código fuente. Por ejemplo, una implementación para el Municipio de Tres de Febrero implicaría solamente el cambio de la paleta de colores del sistema (de teal/lima a azul/naranja) y de los datos institucionales del header.
  • Trabajo sin conexión (modo offline). Actualmente, el sistema requiere conexión a Internet para operar. Una mejora prevista es la implementación de un modo offline con caché local y cola de sincronización, que permita al personal registrar movimientos durante un corte de conectividad y sincronizarlos automáticamente con el servidor cuando se restablezca el servicio. Esta mejora es especialmente relevante dado que la conexión WiFi del CAPS no es siempre estable.
  • Log de auditoría de acciones. Incorporar un registro automático de todas las acciones realizadas en el sistema (quién hizo qué, cuándo y desde dónde), con fines de trazabilidad interna y de rendición de cuentas. Este log permitiría reconstruir la secuencia de operaciones ante cualquier inconsistencia en el stock.
  • Rutina de respaldo automático de la base de datos. Implementar un mecanismo de backup periódico y automático de la base de datos, de modo que ante una falla crítica de la plataforma de hosting se pueda restaurar la información del vacunatorio sin pérdida de datos.
  • Descuento automático de stock desde los sistemas oficiales. En un escenario donde el municipio o la provincia abran interfaces de acceso (APIs) a la historia clínica digital o a la Intranet provincial, el SGV podría integrarse para descontar automáticamente las dosis aplicadas a partir del registro oficial, eliminando la necesidad de la doble carga manual. Esta mejora depende enteramente de decisiones externas al proyecto.
  • Generación de reportes avanzados. Ampliar la capacidad de reportes del sistema con indicadores de tendencia (consumo promedio semanal por vacuna, proyección de agotamiento de stock), gráficos visuales embebidos en el dashboard y reportes comparativos entre períodos, orientados a la planificación de pedidos y a la rendición de información a la Región Sanitaria.

5.2 Requisitos funcionales

Los requisitos funcionales se agrupan por caso de uso. Cada caso de uso describe un flujo completo del sistema, indicando el actor involucrado, las precondiciones, el flujo principal y la poscondición.

CU-01 Autenticación de usuarios

Actor: todos los roles.

Precondición: el usuario tiene una cuenta activa dada de alta por la coordinadora, con un rol asignado.

Flujo principal:

  • El usuario ingresa su correo electrónico y su contraseña en la pantalla de login.
  • El sistema valida las credenciales contra el hash almacenado (bcrypt) en la base de datos.
  • Si las credenciales son válidas, el servidor emite un token JWT con el rol y lo devuelve al cliente.
  • El sistema redirige al dashboard con las funciones habilitadas según el rol.

Poscondición: el usuario queda con sesión iniciada y puede navegar por las secciones habilitadas para su rol.

CU-02 Gestión del catálogo de vacunas

Actor: coordinadora de enfermería.

Precondición: sesión activa con rol coordinadora.

Flujo principal: desde la pestaña Vacunas, la coordinadora puede dar de alta una vacuna nueva (nombre, dosis por frasco), editar sus datos o darla de baja. La baja marca la vacuna como inactiva y ya no aparece en los movimientos nuevos, pero su historial se conserva.

Poscondición: el catálogo de vacunas queda actualizado y refleja el estado real del vacunatorio.

CU-03 Ingreso de un lote nuevo

Actor: enfermería.

Precondición: sesión activa como enfermería; la vacuna existe en el catálogo.

Flujo principal:

  • La enfermera selecciona la opción Ingresar lote desde el menú.
  • Elige la vacuna del catálogo.
  • Carga el número de lote, la fecha de vencimiento y la cantidad de dosis recibidas.
  • Confirma el ingreso.
  • El sistema suma las dosis al stock disponible y registra el movimiento en el historial.

Poscondición: el stock de la vacuna se incrementa en la cantidad ingresada; queda registrado el ingreso con su responsable.

CU-04 Registro de aplicación de dosis

Actor: enfermería.

Precondición: sesión activa como enfermería; existe al menos un lote con dosis disponibles de la vacuna a aplicar.

Flujo principal: la enfermera elige la vacuna aplicada, confirma el lote correspondiente, indica la cantidad de dosis y la fecha, y guarda. El sistema ejecuta la operación dentro de una transacción con bloqueo de fila para evitar concurrencia y descuenta el stock disponible del lote afectado.

Poscondición: el stock del lote se reduce en la cantidad aplicada; el movimiento queda registrado con fecha, hora, responsable y datos del lote.

CU-05 Registro de descarte

Actor: enfermería.

Precondición: sesión activa como enfermería; el lote existe.

Flujo principal: la enfermera selecciona Descarte, elige vacuna, lote afectado, cantidad de dosis y motivo del descarte (rotura, vencimiento, contaminación u otro). El sistema descuenta el stock y registra el movimiento.

Poscondición: el stock del lote se reduce; queda constancia del descarte con su motivo para trazabilidad posterior.

CU-06 Edición y eliminación de un lote

Actor: enfermería.

Precondición: el lote existe en la vista de Stock.

Flujo principal: desde la vista de Stock, la enfermera puede editar los datos del lote (número, fecha de vencimiento, cantidad de dosis) o eliminarlo. La vacuna asociada no se puede modificar para preservar la trazabilidad. La eliminación solo procede sobre lotes sin aplicaciones ni descartes registrados, útil para corregir cargas duplicadas.

Poscondición: el lote queda actualizado o eliminado del stock; la operación se registra en el historial de Movimientos.

CU-07 Consulta del historial de movimientos

Actor: todos los roles.

Precondición: sesión activa.

Flujo principal: el usuario abre la pestaña Movimientos y visualiza el listado cronológico completo, con fecha, hora, tipo de movimiento, vacuna, lote, cantidad y responsable. Puede aplicar filtros por rango de fechas, tipo de movimiento o vacuna, y exportar el resultado a Excel.

Poscondición: el usuario obtiene la información solicitada; no se modifica ningún dato del sistema.

CU-08 Visualización del dashboard con alertas

Actor: todos los roles.

Precondición: sesión activa.

Flujo principal: al iniciar sesión, el sistema recalcula automáticamente las alertas del vacunatorio y las muestra en el dashboard, agrupadas en tres categorías: stock bajo (dosis disponibles menores o iguales al umbral de 10 dosis), próximas a vencer (dentro de los 15 días desde la fecha actual) y vencidas. También se muestran cuatro indicadores clave (KPIs): total de dosis en stock, cantidad de lotes activos, cantidad de alertas activas y movimientos registrados en el mes actual. Las alertas se agrupan en tarjetas por categoría (stock bajo, próximas a vencer, vencidas).

Poscondición: el usuario tiene visibilidad inmediata del estado del vacunatorio.

CU-09 Administración de usuarios

Actor: coordinadora de enfermería.

Precondición: sesión activa con rol coordinadora.

Flujo principal: desde la pestaña Usuarios, la coordinadora puede dar de alta un usuario nuevo (correo, rol, contraseña inicial), editar el correo o el rol de una cuenta existente, resetear su contraseña o desactivarla. La cuenta desactivada no puede iniciar sesión, pero su historial de movimientos se conserva.

5.3 Requisitos de rendimiento

El sistema fue dimensionado según el uso real esperado del vacunatorio del CAPS San José Obrero. Los parámetros de rendimiento son los siguientes:

  • Tiempo de respuesta: las operaciones frecuentes (login, dashboard, registro de movimientos y consulta de stock) deben completarse en menos de 3 segundos en condiciones normales de conexión.
  • Concurrencia: hasta 4 usuarios simultáneos, correspondiente al personal del vacunatorio (enfermería, coordinadora, jefa, proveedora).
  • Volumen esperado: 18 tipos de vacunas, entre 20 y 40 lotes activos por mes, y entre 200 y 500 movimientos mensuales según la estacionalidad de campañas.
  • Retención de datos: el historial de movimientos se conserva sin límite de tiempo mientras el sistema esté vigente.

5.4 Requisitos de la base de datos lógica

La base de datos del sistema es MySQL, con el siguiente modelo lógico de entidades principales:

  • Usuarios: id, correo (único), hash de contraseña, rol, estado (activo o desactivado), fecha de alta.
  • Vacunas: id, nombre, dosis por frasco, estado (activa o dada de baja), fecha de alta.
  • Lotes: id, id de vacuna, número de lote, fecha de vencimiento, cantidad de dosis originales, fecha de ingreso.
  • Movimientos: id, tipo (ingreso, aplicación, descarte, edición, eliminación), id de vacuna, id de lote, cantidad, motivo (opcional), id de usuario responsable, fecha y hora.
  • Frascos abiertos: id, id de lote, fecha de apertura, fecha de vencimiento del frasco (calculada como el menor valor entre 30 días posteriores a la apertura y la fecha de vencimiento del lote), estado (abierto o vencido).

Se definen restricciones de integridad referencial (FK) entre las tablas, unicidad sobre el correo de los usuarios, y transacciones con bloqueo de fila sobre los lotes al ejecutar aplicaciones o descartes para prevenir race conditions.

5.5 Requisitos de diseño

El sistema se diseña siguiendo una arquitectura cliente-servidor full-stack, con separación clara entre las capas:

  • Frontend: HTML, CSS y JavaScript vanilla, con vistas condicionales según el rol activo (mediante la clase role-hidden aplicada con !important).
  • Backend: Node.js sobre Express, con controladores por recurso y validación centralizada.
  • Base de datos: MySQL, con acceso mediante consultas parametrizadas.
  • Comunicación: API REST sobre HTTPS, con autenticación mediante tokens JWT firmados.

El código fuente se aloja en un repositorio Git público, con integración continua hacia Railway: cada push a la rama principal dispara automáticamente un nuevo despliegue.

5.6 Atributos del sistema

Los atributos de calidad definidos para el SGV son los siguientes:

Fiabilidad

Las operaciones que modifican el stock se ejecutan dentro de transacciones con bloqueo de fila, garantizando que un mismo lote no pueda descontarse dos veces por operaciones concurrentes. Los datos se persisten en la base de datos administrada por Railway, con respaldos automáticos.

Disponibilidad

El sistema debe estar operativo las 24 horas, todos los días, con una disponibilidad esperada del 99% mensual. Las interrupciones excepcionales por mantenimiento se comunican con anticipación al equipo del vacunatorio.

Seguridad

Las contraseñas se almacenan como hash bcrypt con sal. Toda la comunicación viaja sobre HTTPS. Las sesiones caducan mediante la expiración del JWT. El acceso está restringido por rol, con un modelo granular de cinco flags de permisos. El sistema no almacena datos personales identificables de pacientes.

Mantenibilidad

El código fuente se organiza en módulos por responsabilidad. El repositorio incluye una documentación técnica web navegable (esta misma) y un manual de usuario con capturas. La bitácora del proyecto registra las decisiones tomadas.

Portabilidad

Al ser una aplicación web, el sistema es accesible desde cualquier navegador moderno sobre cualquier sistema operativo. No requiere instalación local.
